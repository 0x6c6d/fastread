# T050: Restore on every exit path and the leak test

Phase 5 · Model: opus: terminal restore on panic and I/O failure plus goroutine lifetime (R13, R32; Risk "/dev/tty dependence"; Plan row 33) · Depends-on: T049

## Brief
Package `internal/tui` (module `github.com/0x6c6d/fastread`). Existing (keep names and
behaviour): `Run(ctx, t Terminal, p *state.Player, opts Options) (last int, err error)` in
`loop.go` (MakeRaw → `EnterSeq` → loop → deferred cleanup: `RestoreSeq`, `Restore`,
`Close`, wait for the reader goroutine; panics recovered as `tui: internal error: <value>`),
the reader goroutine, the Esc timer and deadline timer, the optional `Resizer` case, seams
`renderFn`, `encodeFn`, `frameHook`, `EnterSeq`/`RestoreSeq`, and the fake terminals in the
test files.

Make every exit path explicit and tested:
1. Exit paths: `q`, Ctrl+C (`0x03`), lone Esc (after `EscTimeout`), ctx cancelled (the
   caller cancels on SIGINT/SIGTERM), end of text, panic anywhere in the loop (render,
   encode, hook, player), `Write` error, `Read` error that is not caused by the cleanup's
   `Close` (e.g. `io.EOF` or EIO from a hung-up terminal), `Size` error. Quit keys, ctx and
   end of text return `(p.Index(), nil)`; the others return `p.Index()` (or 0 if the player
   was not started) and a non-nil error: `tui: reading keys: %w`, `tui: writing frame: %w`,
   `tui: terminal size: %w`, `tui: internal error: <value>`. The reader goroutine reports
   its error to the loop (never blocks on that send once the loop has returned).
2. Cleanup runs exactly once on every path after a successful `MakeRaw`: `RestoreSeq` is
   written exactly once and is the last thing written (also when the panic happened in the
   middle of a frame), then `Restore`, then `Close`; cleanup continues if any of them fails
   or panics; Run returns only after the reader goroutine has exited and both timers are
   stopped. A `MakeRaw` error writes nothing, closes `t` and returns the error.
3. No goroutine other than the reader is ever started by `Run`.

Tests, `internal/tui/exit_test.go` (table-driven; fake terminals record writes, count
`MakeRaw`/`Restore`/`Close` and can inject: panic in `Size`, `Write` error from the n-th
call, `Read` returning `io.EOF` on demand, `Restore` error; `Resizer` on/off):
- `TestRestoreOnPanic` (AC10): `renderFn` replaced by a function panicking on its first
  call and, in a second row, on its third call (after two keys); `encodeFn` panicking;
  `frameHook` panicking. Each: Run returns a non-nil error containing `internal error`,
  does not panic, the output ends with `RestoreSeq`, contains it exactly once, `Restore`
  and `Close` called (≥ 1), `MakeRaw` once; with a `Restore` that also fails, `Close` is
  still called.
- `TestLoopExitPaths`: one row per exit path in rule 1 (incl. `MakeRaw` error) with the
  expected `(last, err != nil)`, `RestoreSeq` count (1, or 0 for MakeRaw), `Close` called,
  and Run returning within 2 s.
- `TestLoopNoLeak` (R32, AC26): baseline `runtime.NumGoroutine()` after `runtime.GC()` and
  one warm-up run; then every row of `TestLoopExitPaths`, each three times, with and
  without `Resizer`; afterwards the count, polled for up to 1 s, is not above the baseline.
  Log the number of runs.

Constraints: change only `internal/tui/loop.go` (and `terminal.go` if the real
implementation's `Read`/`Close` needs it), create `internal/tui/exit_test.go`, extend fakes
only by adding code; all earlier `internal/tui` tests and the `cmd/fastread` tests keep
passing; no `os.Exit`, no `.Fd()`, no Gio, no signal handling in `internal/tui` besides the
SIGWINCH registration in `terminal.go`.

## Verification
`scripts/verify/T050.sh` exits 0. It runs the check command, `TestRestoreOnPanic`,
`TestLoopExitPaths`, `TestLoopNoLeak` and the earlier run/loop tests (also `-race
-count=3`), and in an isolated tmux checks that after `q`, Ctrl+C, Esc, SIGTERM and SIGINT
the pane is off the alternate screen, the cursor is visible, the tty is back in canonical
mode and the exit code is 0. Negative checks: panics and I/O errors restore the terminal
(tests above); killing the tmux pane leaves no `fastread` process.
